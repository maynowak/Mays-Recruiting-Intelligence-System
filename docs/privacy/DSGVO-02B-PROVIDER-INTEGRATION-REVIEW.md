### Source distinction and outcome semantics

- The **integrated pin** contains the internal dispatch and core inspect/export/erase operations, but the reviewed RIS-created `AgentOrder` compatibility path has no subject index linkage. Pin anonymization clears customer fields and subject/index/description but does not clear all nested processing/agent data. It is not safe to attribute current-Main behavior or later reports to this pin.
- **Current Main** adds provider-side consumer/owner/actor identity separation and consumer-scoped privacy filtering, complete GSI2 pagination/full-item fetch, processing-result reporting/export controls, and anonymization removal of result/error/attempt and GSI3 attributes. It still does not remove embedded `agentOrder` in the reviewed anonymization update. The provider source itself, not historical report wording, controls this finding.
- Provider functions are synchronous direct-Lambda operations, not a durable operation API: response `operationId` is not evidence of a persisted/pollable operation ledger. `PREVIEW` is non-mutating; `EXECUTE` requires explicit policy. `BLOCKED`/`PARTIALLY_COMPLETED`, nonzero failed/skipped/retained counts or limitations are not `COMPLETED` for RIS global purposes. An HTTP/Lambda transport success is not a successful domain outcome.
- Provider reports are **historical evidence**, not present deployment proof. `MAYS-ORDERS-PRIVACY-SECRET-E2E-01.md` records a synthetic direct-invoke test with an ephemeral secret that was removed. `MAYS-ORDERS-PRIVACY-FINAL-E2E-ACCEPTANCE-01.md` records P-01–P-03 blocked by missing secret/invoke setup at that point; `MAYS-ORDERS-PRIVACY-FINAL-EVIDENCE-AND-DESTROY-01.md` later records historical synthetic acceptance and cleanup. None establishes today's RIS target deployment, durable secret wiring, IAM invoke grant or current data state.

## 2. RIS integration gaps (not provider feature gaps)

1. **Create-time subject binding:** RIS `agents/orders/real.py::RealMaysOrdersAdapter._create_body()` sends its allowlisted OrderV1 body over the existing HTTP `/orders` contract; it does not send a trusted subject reference. The current provider derives `subjectId` from its own verified JWT subject and rejects body-provided identity. If RIS calls with its own service identity, the indexed subject is that provider token's principal, not automatically the RIS data subject. The integrated pin's AgentOrder route also lacks demonstrated GSI2 linkage. RIS currently has no supported contract to bind the independently resolved RIS/Jobsearch subjectRef to the Orders row. Do not pass a client-supplied subjectId or reinterpret actor/owner identity.
2. **Privacy adapter absent:** RIS has no demonstrated caller for the provider's direct-Lambda internal actions, no provider IAM invoke integration, and no configured/verified secret-delivery path. The provider feature exists; RIS consumption is missing.
3. **Lifecycle semantics absent:** RIS operation orchestration does not yet translate provider PREVIEW/EXECUTE, per-domain results, limitations, counts, retry/timeout ambiguity and partial status into durable resumable outcomes. Do not retry EXECUTE blindly: the provider `operationId` is not shown as a durable reconciliation handle.
4. **Coverage and proof:** no RIS synthetic XRepo test proves a RIS-created order is discoverable/exportable/erasable through the provider at an exact provider SHA. Historical provider acceptance is not that evidence and does not prove deployment configuration.
5. **Policy choices remain open:** whether provider `ANONYMIZE` is sufficient when `agentOrder` persists, and required treatment of legacy unindexed Orders, must remain explicit. RIS must surface unresolved/excluded records, not recreate provider logic.

## 3. Proposed RIS adapter contract (design only)

Implement later in RIS's existing resumable privacy operation path; keep the provider operation in Mays-Orders and use the pin unless a separately approved version change occurs.

- **Create path:** use a provider-approved authenticated service contract to bind the already-resolved canonical RIS subjectRef to the Order. Current public `/orders` contract does not expose trusted subject delegation. Until provider contract supports and tests that binding, RIS must mark Orders subject linkage `BLOCKED/UNAVAILABLE`; never post a client identity or claim coverage. See separate provider CR draft below.
- **Invoke:** invoke provider Lambda only through an approved service role/IAM resource scope. Send action + minimal payload + server-created auth context; secret material comes from an approved runtime secret source, is not persisted with the DSAR operation, and is excluded from logs/errors. The exact provider project/environment and per-action permissions must be bound server-side. No new RIS route that exposes internal provider actions.
- **Inspect/export:** call provider `privacy/inspect` or `privacy/export` with the resolved subjectRef and action-specific authorization. Preserve response status, counts, categories/limitations and operation ID; export payload is sensitive and delivered only through the existing authorized DSAR response path.
- **Erase:** request PREVIEW first and persist only minimized preview evidence; EXECUTE requires explicit human/approved policy gate and approved `ERASE`/`ANONYMIZE`/`RETAIN`. A PREVIEW response does not authorize EXECUTE by itself. Until an explicit decision and provider capability, RIS must not select policy.
- **Map results:** `COMPLETED` is provider-domain success only if no failed/skipped/retained records or limitations conflict with the requested outcome. `PARTIALLY_COMPLETED` remains partial; `BLOCKED` remains blocked; transport errors/timeouts become `UNKNOWN/RECONCILIATION_REQUIRED`, not failure-safe retry or success. `RETAIN` is retained, never erased. Do not auto-retry EXECUTE absent durable idempotency/status lookup.
- **Evidence:** record provider name, exact immutable source pin, action, opaque local operation reference, provider operationId, outcome/counts, timestamps and evidence level. No subjectId, secret, exported payload, raw order body or customer data in logs/receipt. Provider response alone does not prove deployment SHA/configuration.
